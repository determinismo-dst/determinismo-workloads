1. DEVIATIONS

D1. A capture made inside a lookahead at an earlier start position is kept by Java and lost by jank. (new)
  (re-find #"(?=(a))x|b" "ab")                       ; Clojure ["b" "a"]       jank ["b" ""]
  (re-find #".(?!(a))" "aa")                         ; Clojure ["a" "a"]       jank ["a" ""]
  (re-find #"(?!(a))$" "a")                          ; Clojure ["" "a"]        jank ["" ""]
  (re-find #"(?=(a))b|(?=(b))" "ab")                 ; Clojure ["" "a" "b"]    jank ["" "" "b"]
  (clojure.string/replace "ab" #"(?=(a))x|b" "[$1]") ; Clojure "a[a]"          jank "a[]"
  (clojure.string/replace "ab" #"(?=(a))x|b" f)      ; f sees ["b" "a"] in Clojure, "b" in jank (R84 too)
  Mechanism. Java's Matcher keeps one groups array: find() clears it once (search(from)), then the start
  positions are tried one after another without clearing it again, and a lookahead's body (positive or
  negative) returns through its own end node without restoring what its groups captured. So a lookahead that
  captured at position 0 and then failed the rest of the pattern leaves its capture for a match at position 1.
  libstdc++ starts every start position from the results the search began with:
  _M_search (regex_executor.tcc 41–57) calls _M_search_from_first per position → _M_main_dispatch(__dfs)
  (84–92) sets `_M_cur_results = _M_results`; _M_results is written only by _M_handle_accept (429–) when it
  accepts (and `__glibcxx_assert(!_M_has_sol)` there: nothing explores after a solution), so what
  _M_lookahead (151–167) copied into _M_cur_results at a failed position is gone.
  Within one start position the two agree: libstdc++ also keeps a lookahead's captures after the rest fails
  (`(re-find #"(?:(?=(a))x|a)" "a")` is ["a" "a"] on both, `(re-matches #"(?=(a))x|ab" "ab")` ["ab" "a"]).
  Path (jank): core.jank re-find 6378 → core.cpp re_find 972–988 (std::regex_search); re-seq 6388;
  re-matches is one position (no effect); clojure.string/replace and split → string_native.cpp 218/226/393
  (regex_replace / sregex_iterator / cregex_iterator: each step a new regex_search).
  Reach: any pattern with a capturing group inside (?=…) or (?!…) whose lookahead succeeds (or, for (?!…), its
  body matches) at a position where the whole pattern then fails, followed by a match at a later position in
  the same find.
  Classified by a spec-side toggle (Java clearing the groups before each start position): with every round-3
  jank toggle on, that toggle alone removes these deviations.
  Spec: Java's behaviour (JDK 23, checked on the JVM; the javadoc's "the captured input associated with a group
  is always the subsequence that the group most recently matched" is consistent with it). Round 3 compared
  captures inside lookaheads only through the whole match (RXJ4), so it could not see this.
  Census: 13,144 of 1,717,065 questions at ≤ 3 lookahead tokens, 178,668 of 39,495,600 at ≤ 4 (section 7).
  Test: uD1-lookahead-capture-from-an-earlier-start. Confidence: high on jank's side (replica + library
  assertion); medium-high that Clojure users rely on Java's result (it is Java's documented "most recently
  matched" rule, not a separately documented guarantee).

D2. nth on a matcher whose pattern has no groups indexes the match string. (new)
  (let [m (re-matcher #"ab" "xaby")] (re-find m) (nth m 0))      ; Clojure "ab"            jank \a
  (let [m (re-matcher #"ab" "xaby")] (re-find m) (nth m 1))      ; Clojure throws (IOOBE)  jank \b
  (let [m (re-matcher #"ab" "xaby")] (re-find m) (nth m 0 :nf))  ; Clojure :nf             jank \a
  (let [m (re-matcher #"" "a")] (re-find m) (nth m 0))           ; Clojure ""              jank throws
  Path: core/seq.cpp nth 648 (and 698) → the matcher is `indexable` (re_matcher.hpp 18) → re_matcher.cpp
  nth 14–22 → runtime::nth(groups, …), where groups is what re_find stored: smatch_to_vector's string for a
  pattern without groups (core.cpp 945–954) → persistent_string.cpp nth 107–147 (a character from the bytes,
  R52). Clojure: RT.java nthFrom 929–930 (`m.group(n)`) and 986–992 (with not-found: `groups > 0 && n <=
  groupCount` else not-found). With groups the vector gives Clojure's answers except "" for nil (R80).
  Census: 6,120 scripts (12 patterns × 17 inputs × 30 scripts of re-find/re-groups/nth): 59 + 70 + 11 + 90.
  Test: uD2-nth-of-a-matcher-is-the-match. Theorem: nth_no_groups_never_the_match (for every match). Confidence: high.

D3. nth on a matcher without a current match is nil (or the not-found value) instead of throwing. (new)
  (nth (re-matcher #"(a)" "a") 0)                                ; Clojure IllegalStateException   jank nil
  (nth (re-matcher #"(a)" "b") 0 :nf)                            ; Clojure IllegalStateException   jank :nf
  (let [m (re-matcher #"a" "b")] (re-find m) (nth m 0))          ; Clojure IllegalStateException   jank nil
  Path: as D2; groups is nil before any find and after a failed one (core.cpp re_find 980), and seq.cpp nth
  648/698 returns nil / the fallback for it. Clojure: Matcher.group throws without a match (both nth forms for
  a pattern with groups; RT.java 929–930, 989–990). re-groups agrees (both throw).
  Census: 1,260 + 410 of the 6,120 scripts. Test: uD3-nth-of-a-matcher-without-a-match-throws.
  Theorem: nth_without_match_nil. Confidence: high.

D4. re-pattern stops at the first NUL of the pattern string. (new; distinct from R83, which cuts the input)
  (re-find (re-pattern (str "x" (char 0) "y")) "xz")    ; Clojure nil              jank "x"
  (re-matches (re-pattern (str (char 0))) "")            ; Clojure nil              jank ""
  (re-pattern (str "(" (char 0) ")"))                    ; Clojure a pattern        jank throws (Mismatched '(' and ')')
  (re-pattern (str (char 0) "("))                        ; Clojure throws           jank a pattern matching ""
  Path: core.jank re-pattern 6352 → core.cpp re_pattern 929–937 → re_pattern.cpp 6–11:
  `regex{ s.c_str(), std::regex_constants::ECMAScript }` → regex.h 494–495 basic_regex(const _Ch_type*) uses
  `_Rx_traits::length(__p)` (strlen). The pattern's text (`str`, `pr-str`) keeps the whole string. A #"…" literal
  cannot hold a NUL (round 2's R1), so only patterns built at run time reach it.
  Replica departure found: round 3's jRePattern/jankEval compiled the whole string; no round-3 alphabet put a NUL
  in a pattern, so no round-3 count changes.
  Census: 353 patterns with a NUL (≤ 3 tokens over a b NUL * | ( ) $ ^ . ?) × 40 inputs × 5 calls = 70,600
  questions: 11,824 deviations classed as this cut; 1,000 valid patterns rejected and 11,400 invalid ones accepted
  through it.
  Test: uD4-a-pattern-keeps-its-nul. Theorem: jankEval4_pattern_nul (★, every call, input, locale). Confidence: high.

D5. print writes a pattern as its bare text. (new, low; same root as R69/R75: printing through to_string)
  (print-str #"a")       ; Clojure "#\"a\""      jank "a"
  (print-str [#"a"])     ; Clojure "[#\"a\"]"    jank "[a]"
  Path: core.cpp print 141–159 (to_string) → re_pattern.cpp to_string 17–25 (the pattern). Clojure:
  core_print.clj 409–429, print-method for Pattern writes #"…" and ignores *print-readably*. `str` agrees ("a");
  `pr-str` agrees except R71's quote.
  Test: uD5-print-of-a-pattern. Theorem: print_pattern_differs (★, every pattern). Confidence: high.

4. STILL LEFT OUT, AND WHY
- Java's CANON_EQ (no decomposed input is drawn), Unicode properties beyond round 3's families under (?U),
  POSIX \p{Lower}/\p{Upper} under (?i) (not drawn). \X (grapheme cluster), \b{g} and \N{…} stay "not compared"
  on the spec side, as in round 3: jank reads \X and \N as the letters (round 3's S31 class), so their questions
  already differ by syntax.
- The for-every-input proof that libstdc++'s DFS executor never changes _M_results without a solution (the second
  half of D1's mechanism) did not check: a tactic walk over the replica's dfs (12 handlers, StateT over Except)
  reached every leaf of most handlers but left goals, and the file is kept aside unchecked in
  .r4-scratch/regex/ExecInv.lean.unfinished (not in the build). The invariant rests on reading the source and on
  libstdc++'s own assertion (_M_handle_accept: __glibcxx_assert(!_M_has_sol)); the censuses exercise it.
- Lookbehind, inline flags, named and atomic groups only ever meet R18 on jank's side: libstdc++'s scanner rejects
  every "(?" other than "(?:", "(?=", "(?!" (regex_scanner.tcc 136–150), so their matched semantics change no
  comparison; they are matched now so that the spec model has no "not compared" class.
- Thread-safety of a shared matcher (Java documents Matcher as unsafe for concurrent use; jank's re_find mutates
  without a lock): not a deviation from documented behaviour.
