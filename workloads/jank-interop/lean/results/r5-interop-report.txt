The common root of F1-F6: jank gives C++ operands value categories of its own.
  - processor.cpp build_cpp_call 565-572 turns every argument type that is not a pointer, reference or builtin
    into `T&`, and CppInterOp's AddOverloadCandidates (CppInterOp.cpp 2022-2026) makes `T&` an lvalue: a class
    TEMPORARY (`(cpp/T. …)`, a C++ prvalue) is an lvalue to overload resolution (F1, F2).
  - A builtin argument keeps its non-reference type and is a prvalue (2022-2026), also when it is a NAMED variable:
    a `let`-bound local's binding type is its init's type (analyze_let 2414-2421, local_reference.cpp 29-32), the
    result of `cpp/aget` or `cpp/=` is typed by `getType()` without its value kind (CppInterOp.cpp 7101-7130)
    (F5, F5b).
  - Codegen names every operand (`auto t(lit)`, cpp_processor.cpp 1278-1285; `T t(args)`, 1655-1726; `auto &&t(…)`
    for values): the emitted C++ sees lvalues. `cpp_call` wraps an argument in `std::move` when the chosen
    function's parameter is an rvalue reference (1410-1417), `cpp_member_call` never does (1730-1775) (F3, F4).
  - GetBuiltinOperatorType makes every operand except a non-reference nullptr_t an lvalue (CppInterOp.cpp
    7080-7087); round 3 noticed `(cpp/= 1 2)` type-checks (IA5 contradicted) but reported no deviation (F6).
  Clang then compiles the emitted text and resolves the call again from those lvalues (or xvalues), so the
  function the JIT calls can differ from the one jank analysed (F2, F4) or not exist (F3).

    jank's object conversion for a member found through the base is never exact; C++'s for a using-declared member

  - The emitted C++ is judged by C++ rules ("JIT error" = Clang rejects the emitted text), as in rounds 3-4.

     a using-declared base member is the derived class's member for the implicit object parameter

  P4 built-in `=`, compound assignment and prefix `++` need a modifiable lvalue left operand ([expr.ass]/1,
     [expr.pre.incr]/1); unary `&` an lvalue ([expr.unary.op]/3).
