1. DEVIATIONS
======================================================================
E1. \b and \B next to a combining mark. (new)
  (re-find #"e\b" "e\u0301")                        ; Clojure nil              jank "e"
  (re-seq #"\b\w+\b" "cafe\u0301 x")                ; Clojure ("x")            jank ("cafe" "x")
  (clojure.string/replace "nai\u0308ve" #"\b" "|")   ; Clojure "|nai\u0308ve|"  jank "|nai|\u0308|ve|"
  (re-find #"\b" "\u00e9\u0301")   (re-find #"\b" "\u0661\u0301")   ; Clojure ""   jank nil
  (A mark after a non-ASCII letter or digit is a word character to Java, so a boundary appears between é or ١
  and its mark; jank sees no word byte there. \B next to a mark also differs, but each jank \B match inside a
  mark splits its bytes, so those questions count under R78.)
  Java: Pattern.java Bound.check (5543-5593) counts a character as a word character when isWord(ch) holds
  (ASCII [a-zA-Z0-9_], or CharPredicates.WORD() under (?U)) OR when it is a non-spacing mark
  (Character.getType == NON_SPACING_MARK) and hasBaseCharacter (5599-5613) finds, walking back over marks, a
  Character.isLetterOrDigit code point. This holds in every mode, (?U) or not, on every JDK (JDK 19 changed
  isWord to ASCII, not the mark rule). So decomposed text (NFD: macOS file names, text from some input methods
  and normalizers) has no word boundary between a letter and its accent, and a mark after a non-ASCII letter or
  digit (é, \u0661) makes a boundary there.
  jank: core.jank re-find 6379 -> core.cpp re_find 972-988 (std::regex_search); re-seq 6389; clojure.string
  replace -> string_native.cpp 218-233 (std::regex_replace / sregex_iterator). The std::regex is
  regex{ s.c_str(), ECMAScript } (re_pattern.cpp 9) under the global locale std::locale("") (c_api.cpp 1110).
  \b is _M_word_boundary (regex_executor.tcc 551-571) with _M_is_word (regex_executor.h 159-164):
  isctype(byte, lookup_classname("w")) per byte, and bytes 0x80-0xFF have no ctype class in a glibc UTF-8 locale
  (round 3's RXA1), so the mark's bytes are non-word and a boundary falls between "e" and U+0301.
  Not R78 (bytes for characters): matched over code points with the same ASCII \w, jank would still put the
  boundary there. The census classifies it by a spec-side toggle (Java's Bound without the mark rule); that
  toggle alone removes every question in the class, after all of rounds 3-4's toggles are on.
  Spec: JDK 23's source above, checked on the JVM (section 7); the javadoc does not describe the rule.
  Test: vE1-word-boundary-and-a-combining-mark (passes on Clojure 1.12.0). Confidence: high on both sides.

E2. Java's Unicode line terminators in `.` and `$`. (extends R78 and R79)
  (re-find #".+" "\u2028")      (re-matches #".*" "\u2028")   ; Clojure nil    jank "\u2028"
  (re-find #".+" "a\u2028")                                   ; Clojure "a"    jank "a\u2028"
  (re-find #"a$" "a\u2028")                                   ; Clojure "a"    jank nil
  Java's line terminators are \n, \r\n, \r, U+0085, U+2028, U+2029 (Pattern javadoc "Line terminators",
  Pattern.java 459-487; DOT() 5897-5905 for `.`; Dollar 3961- for `$`): `.` never matches them and `$` (without MULTILINE) also
  matches before a final one. jank's `.` is libstdc++'s _AnyMatcher<_, true(ECMAScript), _, _> for char
  (regex_compiler.h 368-398), which excludes only '\n' and '\r'; the U+2028/U+2029 exclusions are compiled only
  for wide characters (`if constexpr (!is_same<_CharT, char>::value)`), and U+0085 is no ECMAScript line
  terminator at all. jank's `$` matches only at the end (R79's mechanism).
  Round 3 drew U+0085 among its extra inputs and counted these questions under "bytes (R78)"; round 5 separates
  them by a spec-side toggle (`.`/`$` with only \n and \r), which removes the whole class. U+2028 in `$` is R79's
  class with another terminator; `.` and U+0085/U+2028/U+2029 would differ even over code points.
  Test: vE2-unicode-line-terminators (passes on Clojure 1.12.0). Confidence: high.

(?U) and \p{…}: nothing new. libstdc++'s ECMAScript scanner rejects every "(?" other than "(?:", "(?=", "(?!"
(regex_scanner.tcc 136-150), so every pattern holding (?U) (or (?i), (?u), ...) is a read error / re-pattern
throw in jank: R18. Every \p{…}/\P{…} is a read error ("Invalid range in '{}'"): S31. [[:alpha:]] is a POSIX
class to libstdc++ and a nested class to Java: S29. \w \d \s without (?U) are ASCII on both sides (Java:
[a-zA-Z_0-9], [0-9], [ \t\n\x0B\f\r]; jank: glibc ctype over bytes, nothing above 0x7F in a UTF-8 locale), so
they agree on non-ASCII text up to R78's byte splitting (\W, \S, \D and `.` match one byte of a multi-byte
character). A Clojure program cannot ask for UNICODE_CHARACTER_CLASS other than through (?U) (re-pattern takes
no flags), so no question with Java's Unicode classes can be matched by jank. Low yield, as expected.

2. PROOFS
======================================================================
Round 4's kept-aside proof (.r4-scratch/regex/ExecInv.lean.unfinished) is finished, in
Jank/R5/Regex/ExecInv.lean (no sorry, no native_decide, no new axiom: results/r5-regex-axioms.txt).

What is proved, for every Ctx (NFA, input buffer, end, step budget, round 3's EFix toggles), fuel, mode, state
index, tail flag and executor state; only runs that return (.ok) count, an aborted run (fuel or budget) is no
result:
- ★ dfs_keeps_res: a run of _M_dfs that starts without a solution and ends without one leaves _M_results (res)
  as it found it.
- ★ searchFromFirst_fail_keeps_res: a start position of _M_search that finds nothing leaves _M_results as it was.
- ★ search_found_from_initial_results: when _M_search (regex_search's DFS path) finds a match, the match is the
  result of a single _M_search_from_first run from a state whose _M_results are the ones the search began
  with; by round 4's searchFromFirst_starts_clean that run starts with _M_cur_results = _M_results.
- ★ search_fail_keeps_res: a search that finds nothing leaves _M_results as it was.
- loop_found: the same for the loop over the later start positions.

What it makes complete: U35's jank side is now a statement about every NFA and every input, not a census: in a
match jank returns, every capture was made during the one start position that matched, starting from the
search's initial (unmatched) results, so a capture a lookahead made at an earlier, failed start position never
appears (the mechanism behind (re-find #"(?=(a))x|b" "ab") giving ["b" ""]). Each step of jank's re-seq,
replace and split is a fresh regex_search (regex_iterator), so the statement holds per step. The Java side of
U35 (find() clears the groups once and keeps a capture from an earlier start position) stays a model checked on
the JVM, as in round 4; round 4's censuses (13,144 of 1,717,065 and 178,668 of 39,495,600) are instances.

How: three properties of a computation at a state (Kat: keeps hasSol and res; Gat: started without a solution,
ends without one only with res unchanged; Hat: Gat, and a solution once found stays), one lemma per kind of step
(get, set, modify, setCurRes, a call into dfs by the induction hypothesis followed by an H-continuation, a guarded
call, the lookahead's sub-executor whose state is replaced by the caller's, _M_handle_accept with and without a
solution, if, associativity), and a walk over dfs's unfolded body (induction on fuel). Why round 4's attempt
failed, and two traps met here: round 4's one-macro walk simp'ed the whole StateT term and met a goal in
function-application form; a simp/dsimp with setCurRes over the whole body timed out; and at default
transparency `refine Gat_get ?_` unified `get >>= ?f` with an `if` by a first-order approximation
(?f s s := the if), which made the walk loop without progress. The walk now unifies at reducible
transparency only, keeps dfs irreducible, and tries the `if` lemmas first.
