Round 6, area W: strings and characters (exe jank6-str). jank main 94d32623 (upstream-r5/), compared
with Clojure 1.12.0. Paths are upstream-r5/compiler+runtime/<path>. Every item is a hypothesis from a
Lean replica re-read against the source; jank was not built or run. Every Clojure value below was run
on Clojure 1.12.0 (results/r6-str-clojure.txt).

The one-paragraph answer
- jank strings are UTF-8 bytes (jtl::immutable_string); every function that takes or returns an index
  counts bytes: count, nth, get, contains?, subs, clojure.string/index-of and last-index-of
  (persistent_string.cpp, string_native.cpp). jank characters are code points (or whatever bytes they
  were built from): seq/first/rest/vec/reverse walk code points (persistent_string_sequence.cpp).
  Clojure counts and walks UTF-16 code units.
- So there are two design choices: (A) byte indices, (B) code-point characters. LG3 is (A).
  Round 2's R52 model predicts LG3 exactly (theorem lg3_model): jSubs "é-è" 2 = "-è".
- (A) and (B) together give R53: jank's (count (seq s)) = (count s) iff s is ASCII (proved).
- Everything else here is a separate defect inside jank's own model, mostly in functions that walk a
  string (escape, replace "", trim, capitalize, the string seq's = and hash), each with a local fix
  (11 diffs written), plus hash and naming defects found on the way (W7, W20).

(1b) One design choice, or separate? (the grouping of section 1)
========================================================================================================
Design A, byte indices (persistent_string's count/nth/get/contains/substring and string_native's
index_of/last_index_of all work on jtl::immutable_string offsets): W1 (LG3), W2, W3, W8, the values in
W9 and W10, and R52 and R58's byte results ((index-of "éa" "a") is 2). In walk A (n <= 6, 137,257
texts) every disagreement of count/nth/get/contains?/subs/index-of/last-index-of without a
supplementary character disappears under the code-point design (column "code-point design != Clojure
(BMP-only texts)": 0 for every op).

Design B, code-point characters (a jank character is a code point; Clojure's is a UTF-16 unit, so an
emoji is one character in jank and two in Clojure, and a lone surrogate exists only in Clojure): W13,
W14, W15, W16 (128512), R53's difference from Clojure on emoji, R57's sign (UTF-8 order puts a
supplementary character after U+E000..U+FFFF; UTF-16 puts it before), R64's surrogates. These remain
under any fix short of UTF-16 strings (cp_design_supplementary; walk A's residual column: every residual
holds a supplementary character).

A and B together: R53. jank's (count (seq s)) is the number of code points (seqCount_jstr, proved). It
equals jank's (count s) iff s is ASCII (seqCount_eq_count_iff), and Clojure's (count (seq s)) iff s has
no supplementary character (seqCount_eq_clojure_iff).

Separate defects (a function inconsistent with jank's own model). Local fix in brackets:
- the cut: subs (and nth/get) can split a character, and what follows differs by consumer: W4 (the case
  functions drop it or throw), W5 (reverse throws), W6/R54 (the seq walks past the end) [R54a; R52a
  was considered and withdrawn, see (11)];
- R55, V48: the string seq's = compares its bytes with the other side's characters [R55a];
- R56: the string seq hashes its raw bytes, not its characters [R56a];
- R57 value and order [R57a strings, R57b characters: exact Java values];
- R58/W11: negative or past-the-end starts [R58a];
- R59: trim/blank? use C isspace [R59a trim, R59b blank?];
- R60: per-code-point locale case mapping, no SpecialCasing (ß, final sigma) [no local fix written];
- R61: capitalize upper-cases a byte [R61a];
- R62: replace "" goes between bytes [R62a]; W12, the same cut in split [regex area];
- R63: escape looks up bytes [R63a];
- R64's C-locale part, R66 (the wrap), R65, R67, W7, W19, W20 [local fixes exist; not confirmed or
  not assigned: described in (11)].

(6) Assumptions (StrA6-n) and earlier ones replaced
========================================================================================================
- StrA6-1: glibc x86-64 memcmp returns the first differing bytes' difference for a 1-byte common length
  (the movzbl/subl tails of __memcmp_avx2_movbe/__memcmp_evex_movbe). C guarantees only the sign.
- StrA6-2: the tested jank links libstdc++ 15.3.0 (round 5's pin) and runs under a glibc UTF-8 locale
  (round 2's RB5 for towupper, wcrtomb, mbrtowc).
- StrA6-3: GC-allocated objects are zeroed, but a temporary small string's bytes after the terminator
  are whatever was on the stack. That is why W6 names both exception texts.
Replaced earlier assumptions:
- Round 2: "Strings are UTF-8 bytes in jank (documented) ... R53 and R57 reduce to their inconsistency
  with jank's own byte-based count". Clojure's behaviour is the property (rule 5). The book's note is a
  note on the deviation, which is why LG3 and W2/W3 are tested now.
- Round 2, R57: "Only the sign is kept: the docstring promises only negative, zero or positive." Java's
  compareTo documents its value, and Clojure returns it: W9, W10.
- Round 2, jUpper/jLower/jCapitalize: "invalid UTF-8 throws". With libstdc++ 15.3.0 only an `error`
  throws; an incomplete last character is dropped (Cut.lean).
- Round 2, R54: "UB read" becomes an over-read followed by an exception in every case (W6), so b03's
  error confirms R54.
- Round 1: "Long and ASCII-string hashes equal Clojure's." It still holds, but it never covered
  characters (W7) or keywords and symbols (W20), which differ even for ASCII.

(10) Library gaps (sdk/lean untouched)
========================================================================================================
- None blocking. The walks are plain complete enumerations (textsOver, byteStrings) with a per-op
  tally (Tally), not sdk `exhaust`: every case is already minimal at these bounds, and a census needs
  counts, which `exhaust` (stop at the first counterexample) does not give.
- Built here: UTF-16 recombination lemmas (unitsToCps_cstr), a lossless UTF-8 decoder (decodeLossless),
  libstdc++'s from_bytes decoder (fromBytes), and Nat bit facts by `decide` over the small ranges of
  c >>> k (the lead bytes), which avoids a Nat/BitVec bridge.
