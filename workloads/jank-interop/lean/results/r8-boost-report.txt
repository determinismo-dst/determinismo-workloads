Summary of the model correction
- Stock x8, (compare 1M (* P (/ 1M P))) with P = 2^200, is 0 (passes) because boost's Newton inverse of P is ABOVE
  1/P (6.22…2125175E-61 against the exact 6.22…21247160434…E-61), so P·q = 1 + ε with ε < 10^-120, and a product of
  order 0 keeps 121 digits, truncated: exactly 1 (★ x8_stock, stock_inverse_above).
- With S2 the exact quotient (140 digits) is read back by rd_string, which keeps 124 of them (order -61, -61 mod 8 = 3,
  3 + 121), truncated, so it is below 1/P and P·q = 1 - 699·10^-128 (printed 0.99…99301, 128 digits; ★ x8_patched).
- Round 3's limb replica (Jank/R3/Boost/DecFloat.lean) computes all of this exactly: it equals boost on every one of
  74,763 operations here. Round 7's stock prediction for x8 was never run through it: round 7 computed only the
  quotient (results/r7-num-forms.txt, which was right) and predicted the product by reasoning from round 3's S2 text
  ("the inverse is a truncated decimal below 1/v, so every quotient is slightly low"; "Newton with truncating
  products from a low estimate stays below"). That text is false: Newton's x(2 - t) uses the truncated product t, so
  2 - t is too large and the iterate can end above 1/v. So the model that predicted x8 failing on stock is ROUND 7's
  (area N's vN5 and the coordinator's x8 comment), built on round 3's prose, not on round 3's replica.

(2) Proofs (for every input unless marked)
------------------------------------------
Jank/R8/Boost/Spec.lean, about the value-level functions of what the limb code computes (mantissa A = the 16 limbs as
one integer, 10^120 ≤ A < 10^128; value A·10^(exp - 120), exp a multiple of 8):
- ★ keepM_digits: a value read from a decimal string keeps exactly 121 + r digits, r = o mod 8 (o = the order of its
  leading digit): the kept mantissa lies in [10^(120+r), 10^(121+r)).
- ★ keepM_trunc: when the string has more digits (L > 121 + r), the kept mantissa is its first 121 + r digits,
  c / 10^(L - 121 - r), truncated toward zero (c lies in that last unit).
- ★ keepM_exact: with at most 121 + r digits the read is exact.
- ★ mulSpec_norm, ★ mulSpec_trunc: a product of two full-precision values is normalized again and is the exact
  product of the stored operands truncated toward zero at its last kept limb: (o mod 8) + 121 digits of the product.
- ★ addSpec_floor, ★ addSpec_norm: a sum of equal signs is the exact sum truncated toward zero at the result's last
  limb (the shifted-out limbs of the smaller operand and the carry limb are dropped); (o mod 8) + 121 digits.
- ★ subSpec_ceil: a sum of opposite signs is the exact difference rounded AWAY from zero (up in magnitude) at the
  unit of the larger operand's last limb, 10^(e_big - 120); ★ subSpec_exact: exact when both exponents are equal.
- trunc_bounds (lemma).
Jank/R8/Boost/X8.lean (single inputs, decide +kernel, no axioms): p_read, s2_quotient (124 of 140 digits kept),
stock_inverse_above (boost's inverse of 2^200 is above 1/P), s2_quotient_below, x8_stock (product exactly 1),
x8_patched (product 1 - 699·10^-128), six_over_three_stock ((/ 6.0M 3.0M) = 2 - 10^-120: 1.999…9, 120 nines).
Axioms (results/r8-boost-axioms.txt): propext, Quot.sound, Classical.choice (subSpec_ceil via omega); X8's none.
No sorry, no native_decide, no new axiom.
Not proved:
- that round 3's limb replica (rdString, add, mul, sub) computes these functions: checked by search, 50,624 checks,
  0 differences (section 8);
- anything about calculate_inv's error (when the Newton quotient is exact, above or below): searched only;
- S2's text path (to_exact_decimal + rd_string) as keepM of the exact quotient: searched (5,209 pairs, 0 differ); its
  arithmetic core is round 7's exact_sound / exact_complete.

(4) What is not exact
---------------------
- The double estimate inside calculate_inv uses Lean's Float (IEEE binary64, no fused multiply-add). It equals boost
  built for x86-64 on every line; boost built for arm64 with clang's default -ffp-contract=on differs (BoostA8-1).
- Overflow and underflow (exponents near ±2^26) are in the replica but outside the searched range (exponents up to
  a few hundred).
- Exceptions are compared by their text (check.cpp prints std::exception::what()).

(5) Still left out, and why
---------------------------
- A bound on the Newton inverse's error (sign and size): no theorem; the scans show both signs.
- BigInt/BigDecimal operators (big_decimal.cpp 22-45, through text), ratio conversions (big_decimal.cpp 140-144,
  ratio.cpp 535-548), double operands (S6): not S4's question; round 3 and 7 cover them.
- A fix: none assigned. S4 cannot be fixed inside cpp_dec_float<N>: a larger N moves the threshold, nothing more. A
  representation as Java's (an unscaled cpp_int and an int scale; area D's scale work) makes + - * and exact division
  exact and removes every S4 test here; the literal must then be parsed into the cpp_int directly, not through
  rd_string, and S2's exact_divide should return that representation instead of text read by rd_string (which
  re-cuts it: vB7).

(6) Assumptions
---------------
- BoostA8-1 (new): jank's BigDecimal code runs without FMA contraction: Linux x86-64 with no -march
  (CMakeLists.txt 141-147), generic x86-64 has no FMA. Evidence of the alternative: boost built for arm64 with clang's
  default contraction differs from the replica (and from x86-64) on 14 of 8,509 Newton divisions (9 of 5,209 `div`,
  5 of 3,300 `pq`), in the last digits; with -ffp-contract=off it agrees on all. The only a + b·c expression on that
  path is extract_parts' `mantissa += data[i] * scale` (cpp_dec_float.hpp 1558), which feeds the double
  estimate. Example: (* 2^160 (/ 3M 2^160)) is 3.00…001 on x86-64 and exactly 3 on arm64. A jank built on macOS
  arm64 can print other digits for such quotients; no test here depends on one (x8 and vB1-vB7 agree on both).
- BoostA8-2 (new, read): jank divides lvalue decimals (math.hpp div `typed_l->data / r`, big_decimal.cpp 44,
  ratio.cpp 542), so an integer divisor is converted exactly (default_ops 569-574). An rvalue on the left takes
  no_et_ops 482-489 → eval_divide(cpp_dec_float&, long long) (cpp_dec_float.hpp 3244-3254) → div_unsigned_long_long,
  a short division: (/ 6.0M 3) would be 2.0 there. check.cpp's first `divl` used an rvalue and differed from the
  replica on 341 of 1,000 lines; with an lvalue, 0. No jank path divides an rvalue decimal by an integer.
- Earlier ones: round 3's MPA set stands; NumA7-2 (a native integer meeting a decimal gives its boxed form's value)
  is consistent with BoostA8-2; NumA7-3 ("the S2 fix stores an exact quotient through its text, rd_string keeps
  ≤ 128 digits by truncation") is replaced by the exact rule: (o mod 8) + 121 digits, truncated.
