(2) PROOFS (statements in words; Lean names)
======================================================================
Jank/R9/Err/Catch.lean (C++ handler matching on the thrown values and handler types jank uses):
- fixed_eq_spec: for every handler list and every thrown value, the code A34 (or V7a) generates
  (the nested try, literally: pass-through handlers, object pass-through, converters, then the
  program's handlers) behaves as the specification: the first handler that matches natively wins,
  and the first object handler also takes every value the variant converts, bound as the
  converted ex-info.
- fixed_stock_eq: with nothing converted, the generated code is the stock code.
- fixed_eq_stock_of_not_conv: for every value not converted (objects, C++ ints, foreign values),
  A34's code does exactly what stock does (no regression).
- fixed_eq_stock_of_earlier: when a handler before every object handler matches the value
  natively (jank's suite cpp/try/pass-catch-mixed.jank), stock and A34 give it that handler.
- spec_eq_stock_of_none, spec_eq_stock_of_not_conv: without an object handler, or for a value not
  converted, the specification is the stock code.
- a34_object_sees: if no handler before the first object handler matches, every error_ref and
  std::exception reaches that object handler as the converted object.
- convErr_observed, convStd_observed: the object's ex-message is the error's message (what() for
  a std::exception), ex-data nil, and an error stays attached.
- vb_outcome_a34 / vb_outcome_stock_err / vb_outcome_stock_std: the tests' `vb-outcome` answers
  :object with A34 for every error_ref and std::exception; stock answers :error / :native.
- thrown_a34 / thrown_stock: `thrown?` sees each of them with A34; stock lets them escape.
Jank/R9/Err/Paths.lean:
- report_preserved: an error crossing any number n of program catches that rethrow (load-lib's at
  each nested require) is printed by the CLI, with A34/V7a, exactly as stock prints the bare error.
- report_stock: stock's printing of the same crossing (the catches don't see the error).
- v7r_report: round 8's V7r object (a read-string error) prints as `#error {...}` on stock's
  print_exception and as the error's report with A34/V7a's.
- load_module_unwrap: a nested require's failure that a module's load-lib made an object is, at
  the enclosing load_module, the same error stock returns.
- v18_star_e: for every read, analysis or macro error, *e (and a converted catch) has ex-data and
  an ex-cause with V18; stock has neither.
- v9_data_kept: for every ex-info a module's top level or a macro throws, and every data map, the
  data is reachable through ex-cause with V9 (round 5's jDataWith), whatever the phase; stock: not.
- nth_fixed_eq_clj: with X20 and X20b, (nth coll i) agrees with Clojure for every collection kind
  and every integer index: a value, nil, or a throw an object catch sees.
- x20_miss: with X20 alone, every negative index on every string still throws a std::runtime_error
  (seq.cpp 656-660): g480-g482.
- nth_stock_std: stock's nth throws only std::runtime_errors.
Not proved: that the C++ compiler compiles the emitted text (checked by syntax-only compiles and a
standalone C++ program of the same shape, section 7); that every throw site of jank's runtime is
modeled (the model has classes and types, not sites); V18's message text (abstracted).

(4) WHAT IS NOT EXACT
======================================================================
- Exceptions are compared by kind (object or not), message and data, not by Clojure class.
- V18's outer message ("Syntax error compiling at (file:line:col).") is abstracted in the model;
  jank's position is the token's (round 5: Clojure's is the enclosing list's), so the text
  differs from Clojure's at the column.
- Messages differ from Clojure's (jank's own texts), on every path; not claimed equal.
- `:default` binds nil in jank (round 4/5 note); the model keeps the thrown value and the
  observers ignore a :default binding.
- jank's nREPL server's handle-client (nrepl/server/core.jank 79-105) catches std.exception,
  object_ref, error_ref in that order: with A34 an error_ref from a handler reaches the object
  branch, so its reply's :err is `(pr-str e)` of the ex-info instead of the error's message.
  Modeled by fixed_eq_spec; not a Clojure-facing behavior.

print_exception; context.cpp load_module)
- Design: the catch, once. When a try has a `catch(object_ref &)`, gen(try) wraps the body in an
  inner try: `catch(T) { throw; }` for each handler before the object one, `catch(object_ref
  const &) { throw; }`, `catch(jank::error_ref const &e) { throw
  jank::runtime::to_exception_object(e); }`, `catch(std::exception const &e) { throw ...(e); }`.
  to_exception_object(error_ref): exception_info(e), the error's message, nil data, the error's
  causes as ex-causes. to_exception_object(std::exception): what(), nil data (not ex_info, so
  round 8's V16 `{}` doesn't apply: Clojure's ex-data of a non-ExceptionInfo is nil). Reporting:
  print_exception of an exception_info carrying an error prints the error's report (it printed
  `#error {...}`); load_module returns the carried error, so nested require failures keep their
  report and causes.
- Should pass: r34 (with R34, in round 8's patch), v07b, v07c, d15, u79, v03 (with V3),
  g480-g482, ve1, ve1b, ve2, ve2b, ve2c, ve3, ve3b, ve3c; without V7r also v07, x27, s17, a13,

  value differs: section 5); v15 (no fix); ve6 (E9-1).

  c_api print through print_exception (unwrapped). safe_eval keeps an exception_info as *e, and
